sherLOG

An autonomous root-cause analysis system for production incidents — and a method for proving how often it is right.

02The problem, and the asset that solves it

An AI system that diagnoses production incidents is a crowded idea. Several commercial products exist, and any competent engineer can wire a language model to a logging API in an afternoon. The interesting question is not whether such a system can produce a plausible root-cause narrative. It always can. The question is whether the narrative is true, and how anyone would know.

That question is structurally unanswerable in the commercial setting. In a customer's production environment, nobody knows the true root cause of an incident — that is precisely why the incident needed investigating. So a vendor cannot say "our root-cause analysis is 84% accurate", because there is nothing to score against. Accuracy claims in this space are testimonial by necessity.

The asset

sherLOG owns its environment and injects its own faults. It therefore knows the true root cause of every incident it investigates. That single fact converts the vaguest requirement in this space — guardrails against hallucination — from hand-waving into a measured, graphed, defensible system property.

Everything in the design follows from that. The system is built so that a language model sits inside a structure that constrains it, verifies it, and measures it, rather than one that asks it politely to be careful. Six mechanisms carry that weight:

MechanismWhat it replaces
Fault catalog with ground truth Anecdotal evaluation. Nine declarative faults, each carrying the recipe for injecting it and the truth about what it does.
Hypothesis ledger with pre-registered predictions "Think step by step." Hypotheses must state what would falsify them before evidence is gathered.
Computed confidence A model asked how sure it is. Models emit discrete labels; code does the arithmetic.
Programmatic citation verification A second model checking the first. Four deterministic checks strip claims that fail.
Calibrated abstention A system that always answers. INSUFFICIENT_EVIDENCE is a success state with faults designed to reach it.
Security by type and grant Careful code review. The redaction gate is a type boundary; ground-truth isolation is a database permission.

The one demo that has to work

The entire design is built backwards from a single sentence:

Target demonstration

A reviewer clicks Inject: connection pool exhaustion, then does nothing else. Within roughly 90 seconds the interface shows an SLO breach detected, an investigation opened autonomously, three hypotheses raised with falsifiable predictions, evidence gathered against each, two hypotheses eliminated with cited counter-evidence, a root cause stated with a commit SHA and a log signature, and a proposed fix. They then open the evaluation tab and see the same pipeline scored across every prior run.

03System architecture

Seven planes, kept as separate deployables so each can be demonstrated, tested, and fail independently.

04The target system

Nimbus Store — a minimal e-commerce checkout path. Five services, two datastores, one chaos proxy, roughly 800 lines of application code.

Checkout was chosen because it is the one flow every reviewer already understands, so no explanation budget is spent on the application itself. All of it goes to the diagnosis.

The topology is not arbitrary. It is shaped so that the symptom is never where the cause is. A slow payment provider surfaces as gateway timeouts three hops away. Redis eviction surfaces as Postgres load. A stalled worker surfaces as stale reads with no errors at all. That distance is what makes root-cause analysis harder than alert routing — and if the gateway could name the cause, there would be nothing to diagnose.

Traffic profile

A k6 profile runs continuously. Three of its properties are load-bearing for the fault catalog rather than decorative:

  • Cohort split — 80% small baskets (1–3 items), 20% large (15–30). Tagged in k6 and carried as a header onto every log line and metric label across all five services. This is the sole reason the N+1 regression is detectable.
  • Diurnal shape — a sine multiplier between 0.6× and 1.6× over a 30-minute synthetic "day". Baselines are non-flat, so naive threshold detection visibly fails where burn-rate detection works. A flat baseline would make the detector look better than it is.
  • A deliberate error floor — 2% of requests use an invalid payment method. Without a steady non-zero error rate, any error at all is trivially the incident and the agent never has to reason about a delta.

The log schema, and the two rules everything depends on

{
  "ts": "2026-08-15T14:32:07.412Z",  "level": "ERROR",
  "service": "orders-svc",  "commit_sha": "a3f9c21",  "config_hash": "7d21e0",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",  "span_id": "00f067aa0ba902b7",
  "event": "db.acquire.timeout",  "route": "POST /orders",  "cohort": "large",
  "duration_ms": 3021,
  "attrs": {"pool_size": 3, "waiters": 14},
  "msg": "connection acquisition timed out after 3000ms"
}

1. event is a stable dotted enum, never an interpolated string. Variable data goes in attrs. This makes log templating near-perfect rather than merely good, and it is what makes "this template has never been seen before" a trustworthy signal instead of a noise generator. The shared logging library rejects any event not declared in its enum, so the discipline is enforced at the call site rather than in review.

2. commit_sha and config_hash appear on every single line. These are what let the agent correlate a log to a deploy or a configuration change without a join. Three of the six v1 faults are solvable largely because of the config hash: it is what separates "this service's configuration moved" from "this service is a victim of something upstream".

A decision that looks small and is not

Loki labels are service and level only. Everything else stays in the JSON body and is extracted at query time. High-cardinality labels — trace_id above all — are the standard way people destroy a Loki installation, and at 78 lines per second it would happen within a day.

06Autonomous detection

"Autonomous" has to mean something specific and observable, not "we run it on a cron".

Detection uses multi-window, multi-burn-rate alerting, following the Google SRE workbook. Burn rate — how fast the error budget is being consumed relative to the rate that would exhaust it exactly at the end of the window — fixes both failure modes of a static threshold at once: paging on a harmless spike, and staying silent through a slow bleed.

Each alert pairs a long window (does this represent real budget consumption?) with a short one (is it still happening right now?). Both must be burning. The short window is what stops an alert hanging around for an hour after the incident is over, which is how teams learn to ignore alerts.

AlertLong windowShort windowBurn rateBudget consumedFires within
Fast burn5 min30 s14.4×2%~45–75 s
Slow burn30 min3 min6×5%~10 min
Stated demo compression

The error budget is 6 hours rolling, not 30 days. A 30-day budget cannot burn 2% inside a 90-second demonstration. This compression is declared out loud in the writeup, because the alternative — quietly substituting a static threshold while still calling it burn-rate detection — would be the dishonest version of the same demo.

Correlation before investigation

One fault fires many alerts. A saturated connection pool breaches availability at the gateway and latency at orders-svc within seconds of each other. Without correlation, the engine opens four investigations into one root cause and pays four times to reach the same verdict.

Alerts are grouped by temporal proximity, and the resulting noise-reduction ratio is a real number the project reports rather than a claim it makes. Topology adjacency and signal similarity are the two obvious next axes; the incident boundary is already the right seam for them.

The autonomy loop

detector fires → correlate → dedupe against open incidents
  → create Incident (status=OPEN)
  → enqueue Investigation
  → engine picks up, runs to completion
  → verdict published, incident annotated
  → if unresolved after N minutes, re-investigate with widened scope

Everything after detector fires runs with zero human input. The frontend observes; it does not drive.

07The evidence layer

Seven deterministic tools, not forty-five. No model appears anywhere in this plane.

Every tool returns a typed Evidence object. The model never sees a raw untyped blob, and every evidence object reaches a prompt only through the redaction gate.

The generalisation seam

These seven tools are the entire interface between sherLOG and any monitored system. Swapping Loki for CloudWatch, or Prometheus for Datadog, means reimplementing seven functions behind an unchanged signature — the investigation engine is not touched. A test asserts that the engine never imports application code, so this boundary cannot erode by accident.

Log volume is the risk that would kill this project

At 6.7 million lines per day, no context window survives contact with raw logs. The answer is statistics before sampling: cluster lines into templates, show the agent

template T-014: 4,200 occurrences, up 340% vs baseline
template T-091:    12 occurrences, NEVER SEEN BEFORE

and let it request samples of the specific templates that matter. Templates are ranked by investigative interest rather than by raw frequency, because the highest-count template is almost always a healthy access log — ranking by count would bury the one line that matters under the four thousand that do not.

Crucially, templating runs continuously rather than on demand. A background job maintains a 7-day rolling template table, so log_stats at investigation time is a table read rather than a batch job — and "never seen before" means "absent from seven days of history", which is a claim the project can stand behind, rather than "absent from however much history we happened to fetch".

08The investigation engine

A staged state machine over an explicit hypothesis ledger — deliberately not an open-ended ReAct loop.

Unbounded agent loops wander, burn budget, and produce confident nonsense. More importantly, they leave behind no artifact anyone can audit afterwards. What replaces one here is six stages over a ledger that is persisted, queryable, and rendered directly in the interface.

StageModel rolePurposeExit condition
1. TriagefastClassify the incident, identify blast radius, pick candidate servicesScope defined
2. HypothesizereasoningGenerate 3–5 competing hypotheses with falsifiable predictions, seeded by document retrieval and past similar incidents≥3 hypotheses, each with predictions
3. Gatherfast, parallelOne isolated subagent per hypothesis; each returns structured findings onlyAll tested, or budget reached
4. VerifyreasoningUpdate posteriors from evidence; refute what is refutedOne dominant, or all weak
5. Criticreasoning, fresh contextAdversarial: "here is the conclusion and its evidence — argue it is wrong, and name a better explanation"Critic verdict recorded
6. ReportbalancedCausal chain, cited claims, proposed fix, confidencePasses the citation validator

The ledger, and the single highest-leverage constraint in the design

Each hypothesis carries a statement, a list of predicted_signals, its supporting and contradicting evidence, a status, and a posterior.

predicted_signals are written during Hypothesize, before any evidence is gathered for that hypothesis. That single ordering constraint is what converts the model from a narrator — which will always find a story that fits whatever it was shown — into a falsifier. If a pre-registered signal is later checked and found absent, the hypothesis is refuted mechanically, and no amount of fluent prose talks it back. The ledger rejects any hypothesis that registers no predictions at all, because an unfalsifiable hypothesis cannot be scored.

How the final decision is actually made

This is the part that most distinguishes the system from a wrapper, so it is specified exactly.

The model labels; the code computes. Language models are good at judging whether a piece of evidence supports a claim and bad at arithmetic over many such judgments — asking one for a final confidence number produces a fluent guess. So the model never emits a posterior. It emits a discrete label per (hypothesis, evidence) pair, plus one sentence of rationale that the interface displays:

Verdict labelWeight (nats)
STRONG_SUPPORT+1.4
WEAK_SUPPORT+0.5
NEUTRAL0.0
WEAK_REFUTE−0.5
STRONG_REFUTE−1.4
DECISIVE_REFUTE−4.0

Code maps labels to fixed log-likelihood ratios and updates in log-odds from a uniform prior, then normalises across open hypotheses. Three guards protect the arithmetic, each closing a specific way confidence gets inflated:

  • Deduplication. Each evidence ID contributes to a hypothesis at most once. Evidence IDs are content addresses — a hash of the query and time range — so two subagents issuing the same query produce the same ID, and this check is exact rather than best-effort.
  • Correlated-evidence cap. Total weight from a single evidence kind toward one hypothesis is clamped to ±2.0. Ten log lines saying the same thing are one fact; without this clamp the log tool alone drives any hypothesis to certainty from a single angle.
  • Mechanical falsification. A missing pre-registered signal is not a model judgment. If the evidence layer checks a predicted signal and finds it absent, code applies a fixed penalty with no model in the loop — deliberately outside the cap, because a failed prediction is not correlated evidence, it is the hypothesis being wrong about itself.

The outcome gate

Pure code. No model is asked what the outcome should be.

if budget_exhausted:        return INSUFFICIENT_EVIDENCE(reason="budget")
if unverified_claims > 0:   mark PARTIALLY_VERIFIED, cap confidence at 0.70
if top.posterior >= 0.80 and margin >= 0.25 and critic == "CONCUR":
                            return CONFIRMED
if top.posterior >= 0.55:   return LIKELY        # capped at 0.79 if the critic dissents
                            return INSUFFICIENT_EVIDENCE(reason="low_confidence")

The margin requirement — the gap between the leading hypothesis and the runner-up — is what makes the confusable fault pairs scientifically meaningful. If two competing explanations both sit near 0.5 because the agent never fetched the signal that separates them, the margin fails and the system abstains instead of coin-flipping. Abstention there is the correct behaviour, and it is only reachable because confidence is computed rather than asserted.

The budget governor

Hard caps, enforced in code and checked before every model call rather than after — checking afterwards means the cap is always breached by exactly one call, and for a reasoning-tier call that is the expensive one.

09The grounding stack

Five layers. The first three are mechanical, and that is the point: do not use a language model to check a language model as the primary defence.

Layer 1 — Structured output, always

Every stage returns a JSON schema. No free-text parsing anywhere.

Layer 2 — Citation binding

Every claim in a report carries the IDs of the evidence licensing it, enforced by schema.

Layer 3 — Programmatic citation verification

The headline guardrail. Four deterministic checks against every claim:

CheckCatches
MISSING_EVIDENCECited IDs absent from this investigation's evidence store — fabricated citations
TEMPORAL_MISMATCHA claimed timestamp outside every cited window — temporal fabrication
NUMBER_NOT_FOUNDA figure in the claim appearing in no cited evidence within tolerance — invented numbers
ENTITY_NOT_FOUNDA service, commit or component named but absent from the cited evidence — invented entities

Claims that fail are stripped, and the investigation is marked PARTIALLY_VERIFIED. The strip-rate is logged and reported. "3.2% of generated claims failed citation verification and were removed" is a measurement; "we prompt it not to hallucinate" is a hope.

Layer 4 — Adversarial critic

Fresh context, sees only the conclusion and its evidence, instructed to falsify. Disagreement caps the final confidence and blocks confirmation outright.

Layer 5 — Calibrated abstention

INSUFFICIENT_EVIDENCE is a success state, and it is reachable in the demo by design. A system that never says I don't know is a system that hallucinates, and any competent reviewer knows it.

10Security architecture

Four mechanisms, each enforced structurally rather than by discipline.

1. The redaction gate as a type boundary

Every evidence object passes through redaction before it can enter a model context. This is enforced architecturally: the LLM client accepts only RedactedEvidence, and only the gate can construct one. The type system does the enforcement, so no future contributor can accidentally route around it — and a test asserts that direct construction fails.

Detection runs in two passes. Named regexes cover known formats (cloud keys, JWTs, connection strings, private key blocks, bearer tokens, emails, card patterns). A Shannon-entropy pass then catches secrets with no known pattern. Redaction preserves the type — [REDACTED:aws_key] — so the agent can still reason that credentials appear at a point in time without seeing the value.

A subtlety worth naming

The entropy pass is gated on charset diversity so that trace IDs, span IDs and commit SHAs survive. A gate that eats trace_id is worse than no gate: it silently removes the field that links a log line to its trace, and the failure mode is a system that quietly gets worse at its job with nobody able to say why.

2. Canary secrets

A known fake secret is planted in a log line, a configuration value, and a corpus document. CI asserts that this string never appears in any outbound model payload, on every build. A green canary test on screen is worth more than three paragraphs about security posture.

3. Egress credential broker

The agent process holds no credentials. Tools call a broker that owns them, validates the calling tool's identity, applies allowlists and per-tool rate limits, and returns only results.

4. Document classification tiers, and prompt-injection containment

Every ingested document carries a tier of public, internal or restricted. Retrieval is tier-gated; restricted chunks return a reference only — "see runbook RB-14 §3, access required" — rather than content. Retrieval over corporate documents is a data-exfiltration surface, and the design treats it as one.

Logs are attacker-controlled input: anyone able to influence a log line can write "IGNORE PRIOR INSTRUCTIONS" into one. Three layers respond. Instruction-shaped patterns are neutralised at the gate. All evidence is wrapped in delimiters with an explicit untrusted-data preamble. And, load-bearingly, the agent has no write capability at all — it reads and reports. The blast radius of a successful injection is a bad report, never a bad kubectl delete.

11The fault catalog

Six injectable faults, two decoys, one abstention case. This is the project's most valuable artifact.

The architecture document targets roughly 15 faults. v1 cuts to six. The reasoning: fault count buys evaluation sample size, not system capability, and sample size is worthless until the pipeline is correct. Six faults spanning four reasoning shapes exercise every mechanism in the design. Faults 7 through 15 are then a data-entry exercise, not an engineering one.

The trap in F-04

F-04 elevates pool waiters too, because blocked handlers hold their connections while waiting on payments. An agent that stops at "the pool is exhausted" gets the proximate service right and the root cause wrong. Ground truth records both proximate_service and originating_component separately, and they are scored separately — collapsing them into "did it find the right service" would hide the exact distinction the fault was built to test.

Two design details that matter enormously

Every injection mechanism is real. No fault is implemented as if FAULT_FLAG: sleep() inside application code. Config faults rewrite the environment and force a container restart, producing a genuine config-hash change. Code regressions apply a pre-authored patch, commit it with a plausible message and author, rebuild the image, redeploy, and write a row to the deployments table. Dependency faults are layer-4 toxics on real network hops. That shortcut would make git correlation and config-diff reasoning fraudulent — the agent would be "discovering" something it was handed — and a technical reviewer spots it immediately.

Decoys run as background noise. D-2 is the more valuable of the two: "there was a deploy right before the incident" is the single most seductive false correlation in real on-call work, and an agent that blames it is doing exactly what a junior does at 3 a.m. D-2 is always injected alongside F-05, so the agent must pick the right commit rather than merely the right time window.

The abstention case

F-07 stops log shipping for payments-svc, then applies a mild latency toxic. Metrics show the service degrading; there are no logs and no traces from the window to establish why. The correct output is INSUFFICIENT_EVIDENCE carrying a stated partial finding — "payments-svc is the proximate service; log evidence is unavailable for this window" — rather than a guess.

Success state  This is the only fault where a confident, well-argued answer is scored as a failure. It must be in the demo.

Ground-truth record

One YAML file per fault, carrying the injection recipe, the root cause, the proximate service, the originating component, the causal chain, the correct class of fix, and the expected signals. One field is worth highlighting:

known_misdiagnosis: "db_pool_exhaustion"   # scored explicitly

This turns "wrong answer" into "wrong answer in the specific way we predicted", which is a far more informative evaluation metric than a binary.

Isolation of ground truth

Ground truth lives in a separate Postgres database owned by an injector role. The investigation engine connects as an agent role which holds no grant on that database at all — not "cannot SELECT", but cannot connect. A CI test asserts the connection fails. A separate database rather than a separate schema, because schema-level separation inside one database leaves a single misplaced GRANT between the engine and the answers.

A second leakage path, easy to miss

The agent's own traces must never land where the agent can read them. If sherLOG's spans went to the same trace store it queries as evidence, it could retrieve its own reasoning as "evidence" about the target system — a closed loop that reads exactly like corroboration — and the injector's spans could leak ground truth by the same route. Mitigation: a separate trace store for sherLOG's own telemetry, plus a hard filter in the trace tool as a second layer. Both are asserted by test.

12The reasoning stack

Framework decision: no orchestration framework

The engine uses the provider SDK directly, with Pydantic for schemas and a hand-written state machine. No LangChain, no LangGraph, no CrewAI, no AutoGen.

The reasoning is short. The design commits to a staged state machine with a hypothesis ledger and explicitly rejects open-ended ReAct. Agent frameworks earn their keep by supplying exactly the thing this project has decided not to build — a dynamic tool-calling loop with memory and routing. What is actually needed is six functions that each take typed input, call one model with one schema, and return typed output. That is roughly 300 lines of our own code, and every line is inspectable at 2 a.m. when a stage misbehaves.

There is a second reason, specific to this project. The thesis is verifiability. Every intermediate artifact — evidence IDs, predicted signals, per-evidence verdicts, posterior updates — has to be persisted, queryable, and rendered in the interface. Frameworks hold that state in their own abstractions and offer a callback surface to get it back out. The time saved on orchestration would be spent fighting to extract the ledger, and we would still not own the schema.

RejectedWhy not, specifically
LangChainIts value is the integration surface — loaders, retrievers, 100+ tool wrappers. This project has exactly seven tools, all bespoke, all querying systems we run ourselves. We would import a large dependency, use ~2% of it, and inherit its abstraction churn.
LangGraphThe closest call and a legitimate choice — the design is a state graph. Rejected because the graph is linear with two loop-backs, and node-level state persistence has to exist in our own schema anyway, so the built-in checkpointer buys nothing. If this later goes multi-agent-dynamic, this is the migration target.
CrewAI / AutoGenBuilt around conversational multi-agent delegation. These subagents do not converse; they are isolated function calls returning a fixed schema.
DSPyGenuinely interesting for prompt optimisation and the wrong shape for an 8-week build — it wants a training set that does not exist until the evaluation harness does. Noted as v2 work: with 200 scored runs, DSPy over the hypothesize stage is a real experiment.

Model routing and the fallback ladder

Stages are routed by role. Concrete model IDs live in a pinned configuration file and are dated versions, never floating aliases — a provider silently updating the model behind an alias mid-project would invalidate every accuracy trend line, and there would be no way to distinguish that from a real regression. The model ID is an experimental variable and is treated as one: changes get a row in a version table and a vertical line on the accuracy chart.

The fallback ladder handles transient errors with exponential backoff, schema-validation failures with one re-ask carrying the validation error, and persistent unavailability by downgrading one rung — and tagging the investigation degraded=true.

The tag is the important part

Any run with degraded=true is excluded from headline accuracy and reported as a separate line. A run that silently fell back to a weaker model is a different experiment, and averaging it into the results is how honest projects produce dishonest numbers.

Determinism, caching, and three run modes

Temperature zero and a fixed seed on every call. This reduces variance without eliminating it, so every fault is run three times and reported as mean ± spread. Evidence is cached by content address; model responses are cached by a hash of model, messages and schema.

How not to fool ourselves with the judge

A model-based judge is the standard way projects like this quietly inflate their own numbers. Two mitigations:

Most metrics need no judge at all. Seven of the nine are exact string matches, set-membership checks, or outputs of the programmatic citation verifier. Only root-cause-text equivalence and causal-chain overlap need a model — so judge exposure is confined to two metrics out of nine.

Where a judge is used, it is audited. It runs at a different model rung than the Report stage used, receives the ground-truth record and a written rubric, and returns a structured verdict. Then 20% of judged runs are hand-scored, and judge–human agreement is published as a headline number. If agreement falls below roughly 90%, the judge is not fit for purpose and the rubric is rewritten before any results derived from it are reported.

The rubric is written in week 0, before any results exist. Grading generously is unconscious rather than dishonest — you look at an answer that is nearly right, and "nearly" quietly becomes "correct" because you know what the system was reaching for. The only defence is writing the definition down while you still have nothing to lose by making it strict.

16What v1 deliberately excludes

The cut line: if it does not make a diagnosis more accurate, more grounded, or more visibly autonomous, it is out of v1.

Excluded from the product

  • Auto-remediation. The system proposes fixes and never applies them. This is also what bounds the blast radius of a prompt injection.
  • Multi-tenancy, RBAC, SSO. Single shared login.
  • Real cloud-provider integrations. Seven tools, all against systems we run.
  • Fine-tuning. Pinned off-the-shelf models throughout.
  • Cross-provider fallback. A second provider means a second SDK, a second structured-output dialect, and — worst — an accuracy number that silently mixes two model families. The seam is left open; v1 does not walk through it.
  • A local model. Ruled out on arithmetic, not preference: four ARM cores with no GPU, already running 9 GB of observability stack. It would be slower than the fault it is diagnosing.

Excluded from the target system

  • No authentication, no real payments, no storefront UI, no inventory reservations, no multi-region, no Kubernetes. The store is a fault substrate, not a product.

Excluded from the catalog

  • Fault-class breadth. v1 has no memory leak, no disk fill, no clock skew, no schema drift, no prompt-injection fault.
  • Each is a YAML entry and an injector method once the harness exists. Backlog order: memory leak (git commit, worker), prompt-injection-in-logs (data), disk fill (chaos), schema drift (git commit).

What makes this defensible

If asked "isn't this just a wrapper around a language model?", the answers are concrete:

  • The fault injection engine and the ground-truth contract — a testbed, not a prompt.
  • The hypothesis ledger with pre-registered falsifiable predictions — a reasoning protocol that mechanically refutes, rather than a model asked to think step by step.
  • Programmatic citation verification — deterministic code that catches the model inventing things, with a measured strip-rate.
  • The evaluation harness — quantified accuracy, hallucination rate and decoy resistance, tracked over time, with ablations that price each design decision.
  • The security architecture — canary-tested redaction, credential brokering, tiered document access, all enforced structurally.
  • Calibrated abstention — the system knows when it does not know, and one fault exists purely to prove it.

The language model is one component inside a system that constrains it, verifies it, and measures it. That is the difference — and it is the sentence the project is built to be able to say.
